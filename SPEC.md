# EASY1 brand hub — product specification

Version: 1.0, 2026-10-14. Status: locked product scope and implementation defaults after two independent static reviews. Technical defaults were adopted by the project owner within the authorized planning scope; they are not attributed to new user approvals. The Editorial layouts/journey and old-tool retirement are user-approved. This lock establishes the implementation contract, not correct application behavior, test-ledger acceptance or permission to publish.

## Purpose and scope

Make easy1staking recognisable as Giovanni's brand for Cardano software, smart contracts and infrastructure, connecting the work to its creator in one place. Brand recognition is the leading goal, supporting product discovery and growth of delegated stake in EASY1. Do not promise a marketing outcome, guaranteed rewards or a date for filling the pool.

The launch includes the homepage, four project overviews, Pool, About, a Coming soon blog index and the delivered brand-media gallery. AdaWatch, AdaMatic and UPLC Link retain their independent identities. Cardano Dev Skills is included as work Giovanni originated and handed to the Cardano Foundation, with that distinction explicit. Product applications stay in their own repositories.

Exclude paid-service offers, hire-me/contact-sales funnels, shithole, the scooper dashboard, DRep/governance pages and actions, and published placeholder articles. No new smart contract, backend, CMS or product-site change is required for this website milestone. Publishing the completed site is a separate operator-directed step.

## Wallet and transaction invariants

W1. Production is explicitly mainnet. Validate the configured SDK chain and fresh CIP-30 wallet network before assessment, review and signing. Undefined/unsupported network input cannot default into a usable client. Encoding identity is immutable, but operational eligibility is not: before building, before signing and after signing before submission, query uncached current pool registration/retirement status observed within 30 seconds. Block if status is unknown, retired or scheduled for retirement. Historical retirement entries do not mean a current retirement; establish the effect of the latest applicable update and current epoch. Metadata ticker corroborates presentation; the fixed pool-key hash remains the transaction identity.

W2. Keep wallet identity, network, stake address, assessment and transaction under one connection revision. Recheck on focus/visibility and every 30 seconds while visible, using a fresh enabled handle. Ignore stale asynchronous results. Recheck before signing and await another fresh context check after signing before submission. An observed account/network/permission change invalidates prepared or signed-but-not-submitted bytes. A change after submission cannot undo it. CIP-30 provides no atomic external-account lock: do not claim that an unobservable switch between the final check and the outward call can be prevented; the reviewed credential, body and witnesses must remain cryptographically bound regardless.

W3. Support ordinary key-controlled stake credentials from a fresh mainnet base/change address. Derive credential A from that address; normalize/deduplicate the wallet reward-address list and select the unique matching credential A, never its first element. If the list is nonempty but lacks A, or the base address is enterprise/pointer/script-controlled or cannot be decoded, refuse with a clear limitation. An empty reward list is permitted only when A is unambiguously derived from the fresh base address and provider registration is independently known; empty is not proof of registration status. Revalidate this binding before build/sign and in the post-sign check. Do not add a new ambiguous credential-selection flow. Keep addresses/API handles/transaction bytes ephemeral and out of analytics/logs; the minimal local recovery record in W7 is the stated exception for transaction identifiers/input references only.

W4. Allow stake-only key-credential certificate shapes: registered A → exactly one pool-delegation certificate (ledger tag 2); unregistered A → one explicit-deposit registration (tag 7) followed by tag 2, or one stake-registration-plus-pool-delegation certificate (tag 11). Every credential is A, the pool hash is verified EASY1, and the registration deposit equals validated current protocol parameters. Reject legacy implicit-deposit registration tag 0, duplicates, deregistration, all other/unknown constructors and vote-bearing tags 9/10/12/13. Tag numbers are taken from the actual ledger CDDL, not an old draft inspection table. There is no vote action or DRep promotion/configuration. No rewards withdrawal, mint, native/Plutus script, collateral, reference input, governance procedure/donation, unrelated payment or new contract is part of this flow. Reject unknown body fields, auxiliary metadata and script data; whitelist only validated inputs, outputs, fee, allowed certificates, validity bounds, explicit mainnet network ID and optional allowed required signers. Protect reference-script UTxOs from selection. For each fresh connection revision, decode the complete unpaginated CIP-30 UTxO snapshot and exact full change-address bytes. Every selected input must be a unique member of that snapshot, controlled by an ordinary payment key, with exact address/value/datum/reference-script content corroborated by the provider and currently unspent. Reject missing, foreign, script-controlled or reference-script inputs. Every output must use exactly the fresh full change-address bytes, with no datum or reference script; matching stake credential A alone never proves payment ownership. Multiple token-bearing change outputs may use that same exact address. Independently sum integer asset quantities: ADA inputs = ADA outputs + fee + validated registration deposit, and each non-ADA input asset sum equals its output sum. No asset can be diverted/burned and no extra payment hidden as change. Validate output minimum ADA and body size against current parameters. Derive the expected witness key-hash set as the deduplicated union of payment keys of all selected inputs and stake key A required by the allowed certificates; body-required signers, if present, must be a subset of that set. Final witnesses must equal that set, all valid over the exact reviewed body; unsupported signer shapes fail closed.

W5. Decode the actual unsigned body before signing, validate its structure/effects, then derive its ID from those exact body bytes. Enforce allowed certificate shapes, credential/pool/network, inputs/change and fee/deposit. A hash helper alone is not a decoder. Ordinary key delegation has no script-execution/reference-script fee: compute the expected linear fee independently from validated protocol coefficients and planned exact witness shape. Enforce an absolute fee ceiling of 500,000 lovelace and maximum 10,000 lovelace over the independently computed minimum. Validate the stake deposit separately; do not describe it as a fee. If parameters/size/witness estimates cannot be validated, block rather than guess. After wallet signing, verify required payment/stake witnesses and signatures; reject empty/partial/unexpected witnesses or any assembled body differing byte-for-byte/hash from review. Recompute the fee bounds using the final serialized signed transaction before submission. Guard limits are documented defaults, not permission for an implementation to raise them silently.

W6. Show target, connected credential/account, exact fee and deposit before approval. A delegation has a finite validity upper bound, 600 mainnet slots beyond the fresh observed construction tip; validate slot/time configuration and refuse expired reviews/signed transactions. Persist the known transaction ID, upper bound and input references synchronously before the first submission attempt, including when submit may time out before returning a hash. Bind reviewed body, signed bytes, ID and connection revision. Acquire one origin-wide `navigator.locks` delegation lock before the decision/build/sign/submit path; the locked path rechecks the shared pending record. The lock is held through the initial submission attempt. If this locking facility/storage cannot be used safely, disable in-site delegation with a clear recovery path rather than offer an unsafe fallback. A cancelled signing request permits clean retry because no outward submission occurred. Show the review expiry; require at least 180 remaining slots before opening wallet approval and at least 120 immediately before the outward submit. The post-sign recheck has a 30-second total deadline, each provider read a 10-second deadline, and submission a 60-second response deadline; deadlines never prove remote rejection. Use a freshly validated tip for the final remaining-slot check. Insufficient remaining validity before any submit discards bytes and requires a new build/review/approval; never extend a signed body. These are conservative allowances, not a guarantee of inclusion within a network deadline.

W7. Distinguish submitted, pending/unknown and chain-confirmed. A returned ID is not confirmation; keep the independently derived ID even if submit returns nothing or a different ID (mismatch is an error). Never automatically sign, resubmit, rebuild or clear an unresolved outcome. A deliberate retry during validity can submit only identical signed bytes for the same ID after reacquiring the origin lock, confirming the record names that ID, and applying body/context/eligibility/remaining-validity checks; another tab cannot retry concurrently. New bytes need new review and approval. A fresh assessment observing EASY1 suppresses another submission and reconciles the known outcome instead. Reload loses signed bytes, so status checking remains available but byte resubmission cannot be invented.

Use one same-origin local recovery record with `{schemaVersion, networkId, poolId, txId, invalidHereafterSlot, inputRefs, createdAt, stage}`; no address, enabled handle, witness/transaction bytes, seed or secret. Share it across tabs via localStorage/storage events and the origin lock. Do not attach its outcome to a newly selected account: show a neutral prior-operation status and block a new delegation while that prior intent is unresolved, even if the user switches wallets. Delete on observed confirmation plus reconciliation with the affected credential's delegation, or authoritative post-expiry evidence that the old transaction was not included and its original inputs remain unspent. A transaction-index 404, new HTTP fetch time or account-index lag is not that proof; if the provider cannot establish a coherent post-expiry ledger point/input state, keep the outcome unresolved and offer status-check/manual-wallet guidance. No blind time-based deletion permits a new fee-bearing transaction. Resolved records and candidates positively known in the current process never to have reached a submission attempt may be cleared under the lock; a reload does not prove a prepared record was never attempted. This is best-effort duplicate suppression conditional on the recovery record being retained and the cooperating origin lock being available; it is not durable exactly-once coordination. Synchronous localStorage success/readback is not a disk-durability acknowledgement. Browser crash, eviction, rollback, private-session end, user deletion, other profiles/devices and external wallet actions are outside the guarantee. Probe storage read/write and Web Locks before action; inspect `navigator.storage.persisted()` where supported as a capability signal, never proof that localStorage cannot be lost. Do not silently add a persistence-permission prompt or coordination backend. If an in-memory pending record disappears/changes unexpectedly, block and retain the known ID; if it disappears across restart it may be undetectable. Explain that pending status is saved in this browser and provide the ID for independent checking. With no retained record, require uncached assessment/history/input reconciliation before a new build, and block visible cross-view inconsistencies; consistent-looking but lagged indexes cannot establish absence. A hard guarantee across storage loss would require a separately approved durable coordination design, outside launch scope. This record is recovery state only, never an analytics/server identifier.

Transaction-context refresh applies to W1–W7 before building, before signing and after signing. Re-read registration/current delegation, pool eligibility, effective protocol parameters, selected-input state and wallet binding with an uncached maximum observation age of 30 seconds. Capture a fingerprint of network/revision, exact change-address/credential bytes, registration and current pool, canonical validated parameter identity/effective epoch, selected input refs/full values/addresses/script content and resolved eligibility. Tip hash/slot/time and response observation ages are a separate freshness envelope: normal tip advancement alone does not invalidate unchanged semantics, but epoch/parameter changes, rollback/incoherent observations, expired/near-expiry validity, unsupported freshness or any semantic fingerprint difference discard the candidate. A newly observed EASY1 delegation yields acknowledgement instead of submission. Registration change, spent/replaced input, changed fee/deposit/min-ADA parameters or unknown state requires a new assessment/build/review; never patch already approved bytes. Cross-view reconciliation checks revealed contradictions and known recent selected-input/delegation history; it does not claim an atomic provider snapshot or prevention of all external-account races.

W8. Failures have plain messages and relevant recovery: missing wallet, denied connection/signing, wrong network, unsupported/ambiguous credential, unavailable provider/configuration, ineligible pool, insufficient funds, inflated fee, changed account, build/body/witness failure, rejected/uncertain submit, expired transaction and pending confirmation. Filter details before logging/rendering so headers, credentials and raw wallet payloads are not exposed. No custody/signing backend is introduced.

Acceptance requires an independent decoder/oracle for actual built bytes, not the builder's own field interpretation. Positive fixtures cover registered/unregistered A and existing representative/Abstain/No Confidence/unset voting states. Mutation fixtures inject tags 9/10/12/13, unknown/duplicate/wrong-credential certificates, wrong pool/network, invalid deposits, inflated fees, withdrawals, mint/scripts/collateral/governance fields, foreign inputs, mixed-payment/stake outputs X/A and P/B, asset diversion, missing/extra signer witnesses, outputs with datum/reference script and reference-script input spending; every one fails before sign/submit. Include reordered/multiple/empty reward-address arrays, non-base addresses, stale revisions, change during wallet approval, malformed/partial witnesses, timeout after accepted submission with no returned ID, cross-tab and reload during index lag, expired-but-unproven outcomes, concurrent same-byte retries, storage failure/disappearance after accepted submission, divergent index views, registration/delegation/parameter/input changes during approval, and 179/180-slot pre-sign plus 119/120-slot pre-submit boundaries. A retained record must block duplicates; loss simulation must expose the limitation rather than pass as durable recovery. No-storage cross-view contradiction blocks; undetectable loss with consistent-looking stale views is an explicitly accepted residual risk. Independent locally funded test-ledger acceptance must show stake target changes while voting state stays unchanged. No automatic test uses real user wallets or submits a mainnet transaction.
